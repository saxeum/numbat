## 1. Goal & non-goals

**Goal:** a repeatable path to add tables + queries with typed migrations, tested
against a real local D1, isolated per environment, without breaking the current
deploy/preview pipeline.

**Non-goals:** authentication (D10) and the actual domain schema — both come
later. Phase 1 builds *infrastructure plus one health probe*; the first real
entity is added when a feature requires it.

## 2. Decisions

| # | Decision | Choice | Notes |
|---|----------|--------|-------|
| P1 | Store | **Cloudflare D1** | architecture D4 |
| P2 | ORM/query | **Drizzle ORM** (`drizzle-orm/d1`) | typed schema + queries |
| P3 | Migration generation | **`drizzle-kit generate`** → SQL files | SQL is plain, applied by Wrangler |
| P4 | Migration application | **`wrangler d1 migrations apply`** | tracked in `d1_migrations` |
| P5 | Test DB | **Miniflare D1** in `@cloudflare/vitest-plugin` | migrations applied per test run |
| P6 | Env isolation | separate DB per environment | prod / preview (+ staging later) |

Rationale for generate-with-Drizzle / apply-with-Wrangler: Drizzle Kit produces
readable SQL and snapshots; Wrangler owns per-environment application and the
migration ledger. Avoids `drizzle-kit push` (no review trail) in production.

## 4. Binding & configuration

`apps/worker/wrangler.jsonc` gains a D1 binding (databases must be created first —
`wrangler d1 create numbat-db` — which returns the `database_id`):

```jsonc
{
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "numbat-db",
      "database_id": "<prod-id>",
      "migrations_dir": "migrations"
    }
  ]
}
```

Then `npm run types -w apps/worker` regenerates `worker-configuration.d.ts`, so
`Env.DB: D1Database` is typed. `DB` is optional in code until Phase 1 lands
(`DB?: D1Database`) so the health check can report "unconfigured".

### Environment isolation (Phase 5)

Named environments hold their own DB:

```jsonc
"env": {
  "preview": { "d1_databases": [ { "binding": "DB", "database_name": "numbat-db-preview", "database_id": "<preview-id>", "migrations_dir": "migrations" } ] }
}
```

> **Important:** the PR preview job currently runs `versions upload` against the
> **default** (production) config, so preview API versions would share the prod
> DB. Before any write endpoint exists, the preview job must target a `preview`
> environment with its own DB (or previews must be read-only). This is a required
> Phase 5 change — see `workflow-plan.md` W3.

## 5. Directory layout

```
apps/worker/
├── src/db/
│   ├── client.ts        # drizzle(c.env.DB) factory
│   ├── schema.ts        # tables (empty until the first entity)
│   └── queries/         # query functions per resource
├── migrations/          # SQL generated by drizzle-kit (0000_*.sql, meta/)
└── drizzle.config.ts
```

`drizzle.config.ts` (repo-root or worker dir; run from `apps/worker`):

```ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  dialect: "sqlite",
  schema: "./src/db/schema.ts",
  out: "./migrations",
});
```

Generate + apply:

```bash
npx drizzle-kit generate --name <migration_name>   # writes migrations/NNNN_*.sql
npx wrangler d1 migrations apply numbat-db --local # dev
npx wrangler d1 migrations apply numbat-db --remote# prod (gated, reviewed)
```

## 6. Local development

- `wrangler dev` uses a **local** D1 by default (`--local`); state lives in
  `apps/worker/.wrangler/state` (gitignored).
- Apply migrations locally after pulling new ones:
  `npx wrangler d1 migrations apply numbat-db --local`.
- Optionally seed with `wrangler d1 execute numbat-db --local --file seeds/dev.sql`
  (seeds gitignored unless reusable across environments).

## 7. Migrations discipline (workflow-plan W7)

- **Forward-only.** Never edit an applied migration; add a new one.
- **One logical change per migration**, one PR that introduces it.
- Generated SQL is reviewed like code.
- **Production application is explicit and gated** — not implicit on deploy:
  a manual `wrangler d1 migrations apply … --remote` (or a dedicated, approved CI
  step). Deploys and migrations are decoupled so a bad migration can't ship
  silently with code.
- Backwards-compatible changes preferred (add column → backfill → switch reads →
  drop in a later migration).

## 8. Testing (Miniflare D1)

Migration setup mirrors Cloudflare's documented pattern.

`apps/worker/vitest.config.ts`:

```ts
import { cloudflareTest, readD1Migrations } from "@cloudflare/vitest-plugin";
import { defineConfig } from "vitest/config";

export default defineConfig({
  plugins: [
    cloudflareTest(async () => ({
      wrangler: { configPath: "./wrangler.jsonc" },
      miniflare: {
        bindings: { TEST_MIGRATIONS: await readD1Migrations("./migrations") },
      },
    })),
  ],
  test: { setupFiles: ["./test/apply-migrations.ts"] },
});
```

`apps/worker/test/apply-migrations.ts`:

```ts
import { applyD1Migrations, env } from "cloudflare:test";

await applyD1Migrations(env.DB, env.TEST_MIGRATIONS);
```

`apps/worker/test/env.d.ts` augments the provided env:

```ts
declare module "cloudflare:test" {
  interface ProvidedEnv extends Env {
    TEST_MIGRATIONS: D1Migration[];
  }
}
```

Tests hit the real Worker via `SELF.fetch(...)`, so routes + D1 run in `workerd`
with isolated storage per test.

## 9. Health check

Enable the stubbed `database` field in `HealthResponse`:

```ts
try {
  await c.env.DB.prepare("SELECT 1").first();
  database = "healthy";
} catch {
  database = "unhealthy";
  ok = false;
}
```

Return `503` when unhealthy. Update the integration test to assert the field.

## 10. CI

- **Tests**: no change beyond Phase 3 — the setup file applies migrations to the
  local D1 automatically on every `npm test`.
- **Migration check**: add a step that fails if `drizzle-kit generate` would
  produce a diff (schema and migrations out of sync).
- **Deploy**: production migrations remain a **separate, gated step** (§7); the
  CI token will need **D1:Edit** added when we automate it.
- **Previews**: Phase 5 routes preview versions to the `preview` DB.
